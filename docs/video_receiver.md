# RMUL 图传接收

## 操作

选择 RMUL 并进入后自动监听已保存的图传配置；没有画面时采用明亮中性灰背景，
中央显示小图标、实际等待/暂停/中断/故障状态和简短说明，可点击 Esc 菜单入口。
不显示网格、圆环、大字英文或边角常驻装饰；监听端点等详细信息放在菜单中。
收到可显示帧后仅隐藏视频占位，断流清屏后恢复占位；业务叠层始终独立存在。
画面按原始宽高比（包括样本宽高比 SAR）居中，尽量铺满窗口，空余处留黑；不拉伸、不裁切。
窗口调整只改变画面显示区域，不改变 UI 档位。

### 右上角实时诊断

RMUL 右上角单行诊断独立于视频和业务层，菜单打开、无图或断流时仍可见；
不拦截点击。字号只按 UI 档位变化，窄窗口省略尾部，完整说明和包/帧计数见悬停提示及运行诊断。

| 字段 | 统计口径 |
| --- | --- |
| RX | 最近 1 秒应用收到并重组完成的帧数，不是 UDP 包数 |
| DEC | 最近 1 秒解码调用产生有效 RGBA 图像的次数 |
| OUT | 最近 1 秒包含新视频纹理的 Qt `frameSwapped` 次数，重复显示/普通 UI 刷新不计入；不是显示器扫描率 |
| 5/1%L | 最近 10 秒完整收帧间隔，按最长间隔排序，取最慢 `ceil(N×5%)` / `ceil(N×1%)` 的平均微秒间隔，再以 `1,000,000/平均间隔` 换算 FPS |
| GAP1s | 最近 1 秒检测到的前进帧编号缺口数 / 编号跨度；处理 16 位回绕，首帧、倒退和半区间跳变不推断缺失 |
| UDP | 精确包损不可测，显示 `—`；协议无分片总数、允许变长负载，不能假设每包 1392 字节来计算 |
| Mb/s | 最近 1 秒所锁定来源的数据报字节数 ×8，包含 8 字节协议头，不含 IP/UDP 头 |
| ms CPU | 最近 1 秒平均软件解码调用耗时，含 RGBA 转换；不含 UDP 等待、纹理上传或端到端延迟 |

low 至少需要 20/100 个已完成间隔，样本不足显示 `—`；停流中尚未结束的间隔也参与排序，
避免冻结在历史高值。完整停包 1 秒解除来源时清理来源统计，重新观察；停止/重配清空全部统计。
GAP 将缺口归入检测它的窗口，包含发送端跳帧、包丢失、超时和本地淘汰等原因，不能据此判断网络丢包。
没有后续帧时无法从序号推断未发送/未收到的帧数，不使用标称 60fps 补造缺失。
非法包、在途重复分片、未完成帧在运行诊断显示最近 1 秒增量；它们不是网络丢包数量。

统计使用本机单调微秒时基；1 秒速率使用 10ms 分桶（窗口边界误差小于一个桶），
low 最多保留 4096 个间隔，超限保留最新样本，工作线程每 250ms 发布一次值副本。
接收、重组和解码仍在同一工作线程，RX/low 包含解码阻塞及批量读包的影响，
不代表网卡硬件接收时间，不能仅凭 RX 下降就认定发送端慢。OUT 另用呈交回调计数，
跨 GUI/渲染线程只共享受锁保护的有界统计，不跨线程访问 QML。

### 软件与硬件解码边界

当前 CPU 执行 FFmpeg HEVC 解码和色彩转换，属于软件解码；Qt 使用 GPU 渲染纹理不等于硬件解码。
接收与组帧可沿用，`HevcDecoder` 可以扩展 FFmpeg 硬件设备/帧上下文，但现有实现没有自动硬解能力。
Windows 可评估 D3D11VA，Ubuntu 可评估 VAAPI，NVIDIA 可评估 NVDEC/CUDA；
是否可用取决于 FFmpeg 构建、设备、驱动和具体 HEVC 格式，不能仅按 Intel i/Ultra 或显卡品牌判断。
NPU 不用于此 HEVC 视频解码路径。
首个可验证实现可将硬件帧下载为 CPU 图像后沿用当前显示接口，但这不是零拷贝；
后续 GPU 纹理共享需单独验证 Qt 渲染后端、设备一致性、同步和生命周期。
硬解还需运行时能力探测、设备丢失/初始化失败处理及软件回退；本轮没有改变解码器选择或解除并行故障规避。

诊断实现已通过 Windows/Qt 6.9/MinGW 构建、格式和 QML 静态检查，完整 CTest 为 8/8。
人工时钟测试覆盖稳定速率、间隔抖动、low 样本不足、停流、序号回绕、窗口过期与缓存上限；
真实 UDP 回环覆盖统计发布、解码输出、Qt 呈交、断流清空和三种窗口三档 UI 边界。
截图使用项目自产短样本及测试节拍，不是 1080p60 吞吐基准；尚未验证 Ubuntu、实机 GPU 呈交或硬解性能。

Esc 打开/关闭客户端菜单，全屏下仍优先开菜单；F11 切换全屏。
菜单默认进入当前会话，左侧包含图传设置、显示设置和运行诊断；图传只是一个分区。
侧栏始终提供继续画面和返回欢迎页。菜单打开期间继续接收。
图传分区可保存并开始接收或停止接收；关闭菜单不停止图传，也不提交编辑草稿。
同次打开期间切换分类保留草稿，重新打开菜单恢复已保存配置。
返回欢迎页释放监听端口并清空画面；再次进入恢复配置并开始监听。
当前业务叠层为空，详细错误在设置内显示；后续业务字段不属于视频纹理内容。
客户端菜单采用中性灰侧栏和橙色选中/动作色，图传分区保留会话摘要、监听表单及只读协议规格。
会话分区按网络、身份和连接状态分组；会话和图传表单滚动，底部保存/断开动作固定。
菜单居中，中档最大 1120×740 逻辑像素，窗口不足时保留水平 24、垂直 40 像素边距。
文字、图标、按钮高度和菜单最大尺寸只由 UI 档位决定；窗口仅改变可用空间、位置和列宽。
小窗口内容滚动，调整窗口不重置分区或草稿；下拉使用单向箭头和 Qt 键盘导航。
显示分区修改已有 UI 三档和全屏偏好；诊断只展示当前可取得的运行信息。
图传设置仅开放本机监听地址、UDP 端口和首个分片编号。端口可修改，标签明确标注默认 3334，
修改后需与发送端目标端口一致；不会自动通知或修改发送端配置。
协议规格以只读信息显示：UDP / H.265 HEVC、官方 1920×1080 / 60 帧每秒、8 字节大端包头、
每包最多 1400 字节（负载最多 1392 字节）及无重传。这些是协议约定，不是当前流的测量结果。
超时、缓存和解码策略保留为内部策略，不开放编辑。
实际发送端 IP 和 UDP 源端口来自当前锁定来源，只读且不保存；未发现、停止或停包一秒后清空。
来源识别发生在包可进入组帧时，不要求已成功解码，也不表示来源已认证。实际来源不代替本机监听配置。
所有控件使用独立 UI 档位，提供悬停与键盘焦点反馈；小窗口只滚动表单，底部操作始终可见。
RMUC 继续保留原占位页；视频监听不依赖 MQTT。当前会话分区可独立启动 MQTT，见[本地接入](local_integration.md)。
视频生命周期由 C++ MatchSession 统一管理；会话运行时 UDP 绑定与 MQTT 使用同一个本地 IPv4，
视频地址在图传分区只读，UDP 端口仍可改（默认 3334）。停止视频不停止 MQTT，
断开 MQTT 不停止当前视频；离开比赛页停止全部链路，暂停视频不会因 MQTT 重连而重启。

配置保存在 Qt `AppConfigLocation/video.ini`，整组验证、原子保存，写失败保留原会话。
文件损坏时整体回退默认显示值且禁止监听，用户重新保存后恢复。

| 配置 | 默认 | 范围与含义 |
| --- | --- | --- |
| address | 0.0.0.0 | 本机数字 IP；默认所有 IPv4 接口。不是发送端 IP，不解析域名、不加入组播 |
| port | 3334 | 整数 1–65535，官方监听端口 3334 |
| index_base | 0 | 0 或 1，必须匹配发送端；0 是工程初始选择，官方未规定 |

需要允许系统防火墙接收对应 UDP 入站数据；程序不会自动修改防火墙。

## 网络连接与分片编号

官方 §2 指定 MQTT 服务器为 `192.168.12.1:3333`，自定义终端本机 IP 为 `192.168.12.2`。
视频采用独立的 UDP 接收：发送端向终端的 3334 端口发送数据，本程序监听、重组、解码后显示，
没有 RTSP URL、拉流请求或 MQTT 视频订阅。官方该节未单列 UDP 源 IP/源端口，
不能把 MQTT 服务器地址写成已确认的视频源地址。

官方设备接入时，先在系统中把连接裁判系统席位 RJ45 的以太网网卡配置为官方终端地址 `192.168.12.2`，
子网掩码等参数按设备网络说明配置；本程序不会设置系统网卡 IP。
仅视频预览可保留 `0.0.0.0`（所有本机 IPv4 接口）；正式会话会收紧到所选网卡已有的
`192.168.12.2`，端口填 `3334`，保存并接收。`0.0.0.0` 不是发送目标地址，
`127.0.0.1` 仅用于同机测试。设备连接及发送行为仍需官方硬件联调确认。

“首个分片编号”（配置项 `index_base`）表示每一帧内的 UDP 小包从 0 还是 1 编号。
例如同一帧拆成三包，编号可能是 `0,1,2`，也可能是 `1,2,3`；不是帧号、端口或画质选项。
重组器按编号拼回完整帧，再交给 HEVC 解码器。官方没有写明起点，目前 0 是工程初始选择，
必须根据发送端实现或抓包确认，不能声称是官方默认值。普通裸 H.265 / RTP / MPEG-TS UDP 流
不符合本项目的 8 字节包头格式，不能直接接入当前接收器。

## 协议和工程策略

依据 [2027 协议 §2](protocol_2027.md)：8 字节大端头（uint16 帧号、uint16 分片号、
uint32 帧字节数），每包最大 1400 字节，负载最大 1392 字节；标准 HEVC 1080p60，无重传。
按完整 Annex B 访问单元交给 FFmpeg，不能将带头的数据报直接当裸 HEVC 或 MPEG-TS 播放。

下列限制是保护实时链路的工程策略，不声称官方规定：

- 每帧最多 2 MiB / 4096 分片，最多 4 帧同时组装；组帧期限为从首片起单调时钟 150 ms。
- 接受可变长度分片、乱序和相同重复；长度冲突、同序号不同内容、缺片、超时帧丢弃。
  连续分片序号与累计字节数同时满足才输出，绝不将部分帧送解码器。
- 16 位帧号按半区间比较处理回绕；已输出更晚帧后不回放旧帧。
- 单会话锁定首个有效候选来源的 IP + UDP 源端口，避免混帧；该来源停包 1 秒后重新锁定。
  来源或解码帧序列跳变后重建解码器，等待可解码关键帧。
- 一秒没有成功解码画面就清屏，不用旧画面冒充实时视频。收到码流但不能解码时错误留在设置。
- 系统 UDP 接收缓冲请求 8 MiB（实际由 OS 限制）；每轮最多处理 128 包，持续检查停止/超时。

这套策略需用官方发送设备核实分片起始序号、访问单元边界和关键帧恢复行为。

## 线程、缓存与渲染

`VideoReceiver` 由主程序持有，公开方法仅 GUI 线程调用；`sourceAddress/sourcePort` 是 GUI 只读快照。
一个接收线程拥有 QUdpSocket、VideoAssembler 和 HevcDecoder，全程不调用 GUI。
停止请求中断，最多等待当前包/解码完成后 join；socket 与 FFmpeg 资源在该线程退出时释放。
QML engine 先析构，再释放接收器，避免悬空绑定。

FFmpeg 软件 HEVC 解码最大 1920×1080，编解码器内部使用单线程；解码仍在独立接收线程。
实流故障现场显示 FFmpeg 7 的 slice/WPP 并行停在 avcodec_send_packet 内部等待，
GUI 的停止/重配置又同步等待接收线程，造成界面无响应，因此基础路径禁用内部并行。
不启用增加帧排队的 frame threading；1080p60 性能需在目标设备实测。
像素先转换为 CPU `RGBA8888`（8 bit）；YUV 矩阵使用流中 BT.601/709/2020 标记，未标注 HD
使用 BT.709，区分有限/全范围。此基础路径不提供 HDR 色调映射。
显示只用最新帧，不按 PTS 排队；接收、超时以 QElapsedTimer 单调毫秒为准。
没有墙钟同步，不把到达时间声称为相机采集时间或端到端延迟。

跨线程单槽邮箱由互斥锁保护，只发布不可变 QImage，共享后不修改；来源端点也在同锁下按转换发布。
GUI 每 16 ms 取最新帧与来源状态，来源只在获得、改变或清空时通知 QML，
无逐帧/逐包 queued signal 堆积。VideoView 在 Qt 场景图同步阶段上传纹理，纹理由节点持有，
只在新帧/重建节点时上传，窗口缩放只更新矩形。软件场景图也可运行。
用户态组帧最多 8 MiB，加单槽/GUI/纹理每张最大约 7.9 MiB；此外还包括 FFmpeg 参考帧、
解码线程、驱动与系统 socket 缓存，不能把这些数值当进程总内存上限。

## 构建和许可

正式链接 FFmpeg **7.x**：libavcodec 61 / libavutil 59 / libswscale 8，C API。
Windows 使用匹配工具链的 shared SDK，设置 `PIP_FFMPEG_ROOT` 为含 `include/lib/bin` 的前缀；
MinGW 需要 `.dll.a`，MSVC 需要对应 `.lib`。CMake 不会联网下载或引入厂商 SDK。
运行 DLL 优先 SDK，亦可使用当前 Qt kit 附带的同 ABI 版本，构建后复制到应用目录。
必须保证 SDK 头文件、导入库和 DLL 相匹配；发布时随附许可及对应源码获取方式。

Ubuntu 同样需要 FFmpeg 7 开发 SDK；通过 `PIP_FFMPEG_ROOT` 及 `CMAKE_PREFIX_PATH` 指定前缀。
发行版默认 FFmpeg 6/8 不能当作 7 的兼容替代；共享库通过系统安装或部署 RPATH 解析。
本轮没有 Ubuntu 可运行环境，不能声明已经完成 Ubuntu 构建或 X11/Wayland 验收。

本机开发使用 FFmpeg 官方 7.1 源码头文件和 Qt 6.9 随包的 FFmpeg 7 共享库，
由 MinGW gendef/dlltool 生成本地导入库，仅存于忽略的 `.cache/ffmpeg/sdk`；
libavutil/avconfig.h 的目标配置为 Windows x86_64 little endian / fast unaligned。
其他架构必须使用该架构正式生成的 SDK，不能复用此配置。
官方源码：[ffmpeg-7.1.tar.xz](https://ffmpeg.org/releases/ffmpeg-7.1.tar.xz)，
SHA256 `40973d44970dbc83ef302b0609f2e74982be2d85916dd2ee7472d30678a7abe6`。
项目只使用 FFmpeg 内置 HEVC 解码及 swscale，不链接本机测试编码器或 ffmpeg CLI。
FFmpeg 基础许可证 LGPL-2.1-or-later，启用 GPL 组件会改变发行许可，取决于实际构建配置；
许可文本随 `resources/licenses` 保留，分发时必须核对所选二进制的配置和合规材料。

## 预算与验证

目标为官方 1080p60；无缓冲累计、GUI 不做网络/解码是当前必须满足的结构约束。

### 业务叠层边界

`Main.qml` 的 `businessOverlay` 与 `VideoView`、`VideoPlaceholder` 同级，使用窗口逻辑坐标；
它不绑定视频帧尺寸或接收状态，接收、断流、暂停、错误和恢复均不重建此层。
本轮保留空挂载点，没有新增血量、准星或 MQTT 字段 UI。
后续只读展示模型需保留最后有效值并标记未更新，从未收到的字段显示未知；
更换机器人或比赛会话必须使旧身份展示值失效。业务新鲜度不能由视频状态推断。
该展示模型尚未实现；当前 DataPipeline 的失联缓存清理及控制门控保持原有语义。
视觉方案及字体证据边界见[视觉来源审查](design/rmul_visual_reference_audit.md)，
本项目颜色和几何方案不宣称为官方强制规范。

本轮验证基于 320×180 自产 HEVC 样本；尚未验收官方图传设备、1080p60 性能、长稳、DPI、
Windows 原生窗口实机或 Ubuntu。Intel/NVIDIA 硬解、零拷贝和 NPU 均未启用；当前 CPU
基础路径不依赖 NVIDIA，Qt 场景图负责跨平台渲染。硬件加速必须后续按设备探测和实机验证。

## 2026-11-12 实流停止故障修复

Windows 卡死现场确认 GUI 在 configure → stop → QThread::wait 等待接收线程，
接收线程在 avcodec_send_packet 的 HEVC slice/WPP 内部等待；现场为 1920×1080、
thread_count=4、active_thread_type=FF_THREAD_SLICE。基础路径现禁用编解码器内部并行。
该结论来自现场线程栈；没有宣称所有 FFmpeg 7 版本或所有 HEVC 流都会复现。

新增 320×180 / 1920×1080 持续 UDP 负载下各 20 次保存、停止和重开回归，
并通过 MockServer 的真实调试编码流连续 20 次重配置，单次保存/停止/启动约 18–36 ms。
Windows 构建及 6 项 CTest（含离屏 QML）通过。此短测验证当前故障规避路径，
不代替桌面驱动矩阵、1080p60 吞吐、30 分钟长稳及 Ubuntu 验收。
MockServer 曾出现的编码器 TCP EOF 是另一条故障证据；原始 FFmpeg 日志缺失，
不能断言它由客户端停止引起。发送端已补充退出码和 stderr 保留，供再次出现时定位。
