# RMUL 图传接收

## 操作

选择 RMUL 并进入后自动监听已保存的图传配置；没有画面时采用明亮中性灰背景，
中央显示小图标、实际等待/暂停/中断/故障状态和简短说明，可点击 Esc 菜单入口。
不显示网格、圆环、大字英文或边角常驻装饰；监听端点等详细信息放在菜单中。
收到可显示帧后仅隐藏视频占位，断流清屏后恢复占位；业务叠层始终独立存在。
画面按原始宽高比（包括样本宽高比 SAR）居中，尽量铺满窗口，空余处留黑；不拉伸、不裁切。
窗口调整只改变画面显示区域，不改变 UI 档位。

### 垂直同步

欢迎页设置或 Esc → 显示设置可修改垂直同步，默认开启，保存后重启客户端生效。
运行中保留当前窗口和视频会话；开关说明显示本次启动请求及是否需要重启。
开启有助于减少撕裂，关闭可能降低呈交等待，实际效果由系统、驱动和合成器决定。
`QSG_NO_VSYNC` 外部环境覆盖也会显示；Qt 6.9 按变量是否存在判断，值 `0` 仍请求关闭。
希望恢复由界面控制时应移除该变量后重启。Qt 请求值与屏幕实际扫描状态分开解释，
不将 Qt `frameSwapped` 当作亮屏时刻。实现及本地验收见[垂直同步验证](design/vertical_sync_validation.md)。

### 右上角实时诊断

RMUL 右上角单行诊断独立于视频和业务层，菜单打开、无图或断流时仍可见；
不拦截点击。字号只按 UI 档位变化，窄窗口省略尾部，完整说明和包/帧计数见悬停提示及运行诊断。

| 字段 | 统计口径 |
| --- | --- |
| RX | 最近 1 秒应用收到并重组完成的帧数，不是 UDP 包数 |
| DEC | 最近 1 秒解码调用产生有效 RGBA 图像的次数 |
| OUT | 最近 1 秒包含新视频纹理的 Qt `frameSwapped` 次数，重复显示/普通 UI 刷新不计入；不是显示器扫描率 |
| OUT 5/1%L | 最近 10 秒含新视频纹理的 Qt 呈交间隔；按最长间隔排序，取最慢 `ceil(N×5%)` / `ceil(N×1%)` 的平均微秒间隔，再以 `1,000,000/平均间隔` 换算 FPS |
| RX 5/1%L | 同一算法，样本来自应用完整收帧；不能代替 OUT low，也不是 CPU 性能评分 |
| GAP1s | 最近 1 秒检测到的前进帧编号缺口数 / 编号跨度；处理 16 位回绕，首帧、倒退和半区间跳变不推断缺失 |
| UDP | 精确包损不可测，显示 `—`；协议无分片总数、允许变长负载，不能假设每包 1392 字节来计算 |
| Mb/s | 最近 1 秒所锁定来源的数据报字节数 ×8，包含 8 字节协议头，不含 IP/UDP 头 |
| C/D/R ms + 后端 | 最近 1 秒 codec 调用 / 硬件帧下载 / RGBA 转换的平均毫秒；CPU 下载显示 `—`，不是 GPU 时间或端到端延迟 |
| 解码最大耗时 | 悬停及 Esc 诊断展示最近 1 秒最大解码调用耗时，避免平均值掩盖偶发长停顿 |
| 排队 / 本地丢弃 | 最近一次有效解码调用开始前等待毫秒；本会话累计的待解码 AU 丢弃数量，包含来源/序号重置和队列溢出，不等于网络包损 |

Esc 运行诊断首项为“首包读出至 Qt 呈交”，直接报告同一帧的均值和 P95 等分位数；
“解码总耗时”也使用整个调用的独立计时，不依赖各子阶段相加。
首包是应用读出首个有效分片的时刻，不含内核 socket 缓冲等待；Qt 呈交不是显示器亮屏时刻。
本地低延迟排查与修复证据见[延迟排查记录](design/video_latency_investigation.md)。

两组 low 各自至少需要 20/100 个已完成间隔，样本不足显示 `—`；停流中尚未结束的间隔也参与排序，
避免冻结在历史高值。完整停包 1 秒解除来源时清理来源统计，重新观察；停止/重配清空全部统计。
GAP 将缺口归入检测它的窗口，包含发送端跳帧、包丢失、超时和本地淘汰等原因，不能据此判断网络丢包。
没有后续帧时无法从序号推断未发送/未收到的帧数，不使用标称 60fps 补造缺失。
非法包、在途重复分片、未完成帧在运行诊断显示最近 1 秒增量；它们不是网络丢包数量。

统计使用本机单调微秒时基；1 秒速率使用 10ms 分桶（窗口边界误差小于一个桶），
low 最多保留 4096 个间隔，超限保留最新样本，工作线程每 250ms 发布一次值副本。
收包/重组与解码分属两线程，RX 不再同步等待解码调用，但仍受系统调度及批量读包影响，
不代表网卡硬件接收时间，不能仅凭 RX 下降就认定发送端慢。OUT 另用呈交回调计数，
跨 GUI/渲染线程只共享受锁保护的有界统计，不跨线程访问 QML。

### 解码设备选择与回退

Esc → 图传设置 → 视频解码设备，可选自动、CPU 或枚举出的各个 GPU 后端。
进入程序时在独立探测线程枚举并初始化 HEVC 上下文；“重新检测”可刷新设备，
不会修改当前选择或中断接收。检测中的重复请求幂等，不在 GUI/收包线程执行驱动探测。
CPU 标签显示处理器名称；同一 GPU 的不同后端可分别出现，不代表两块显卡。
不可用项保留在列表中并禁选，选项下方说明失败原因。

默认自动选择 FFmpeg 7 HEVC 硬件设备：Windows 按 DXGI 顺序枚举非软件适配器，
依次尝试 D3D11VA；Ubuntu 枚举 `/dev/dri/renderD*`，依次尝试 VAAPI。
平台路径不可用时再尝试动态 CUDA Driver API 枚举的 NVIDIA 设备，最终回退 CPU。
这覆盖 Intel Core i / Ultra 核显、AMD 和 NVIDIA 的适配入口，实际可用性仍由运行库、
驱动、GPU 代际和当前 HEVC 格式决定。NPU 不参与 HEVC 解码。
CUDA 必须在所用 FFmpeg 的原生 HEVC 解码器中启用；仅安装 NVIDIA 驱动不能补足构建缺失。
当前客户端只有接收/解码，不新增视频编码功能；设备列表仅表示本机 HEVC 接收能力。

选择使用设备身份 key 保存，接收前重新映射本次驱动编号；不会仅按 GPU 排序恢复旧选择。
Windows 用 DXGI LUID（重启/驱动变更可能失效），Linux 用 DRM sysfs 身份，CUDA 用 UUID。
旧身份失效时保留配置和原因，回退 CPU；需要用户重新选择，不偷偷改用另一张 GPU。
手动指定设备失败也仅回退 CPU，自动模式才依次尝试其他候选。
关闭菜单丢弃未保存草稿，“保存并接收”原子保存监听及设备选择并重启当前视频会话。

设备创建、HEVC 硬件格式协商及真实硬件帧输出分开验证。诊断 `decoder` 在首个硬件帧下载成功前
以 `d3d11va?` 等标识待确认，成功后去掉 `?`；`hardwareActive` 仅在真实硬件帧输出后为 true。
`decoderDevice` 显示适配器名称/编号或 render 节点，`decoderFallback` 保留本会话的候选失败记录。
右上角悬停和 Esc 运行诊断均可查看，不再硬编码 CPU。RX 5/1%L 是收帧间隔统计，
不是 CPU 性能评分，也不是呈交 low；末尾后端仅说明当前解码路径。

初始化、格式协商、硬件解码或下载失败时淘汰该候选；自动模式尝试下一设备，手动模式回退 CPU。
普通非法访问单元不视为设备损坏；仅错误码不足以确定损坏时仍需驱动实测。
回退只重试当前访问单元，不积累旧 GOP；丢失参考帧时等待后续携带参数集的关键帧。
来源超时或帧编号跳变时只重开 codec，保留设备和失败历史，避免网络抖动反复初始化 GPU。
同次接收会话不重新启用已失败后端；停止后重新开始才重新探测。
设备创建和驱动调用在解码线程执行；OS/驱动内部调用没有可移植的强制取消机制，
不能把单次停止测试通过当作任何驱动故障下的最大等待保证。

### 分阶段耗时

Esc → 运行诊断展示以下阶段最近 1 秒的均值、P95、P99、最大值和样本数：

| 阶段 | 起止与边界 |
| --- | --- |
| 首包读出至 Qt 呈交 | 同一帧首个有效分片被应用读出 → `frameSwapped`；含后续分片重组等待，不含内核排队和物理扫描 |
| 解码总耗时 | 整个 `HevcDecoder::decode` 调用，包括 packet 准备、可能的回退、下载和转色，直接计时 |
| 首包读出至组帧 | 首个有效分片读出 → 完整 AU 重组；样本取已进入解码且代数有效的 AU |
| 解码排队 | 完整 AU 重组完成 → 对该 AU 开始解码 |
| 编解码器调用 | `avcodec_send_packet` 与 `avcodec_receive_frame` 的累计同步调用耗时，包含其内部驱动等待 |
| 硬件帧下载 | `av_hwframe_transfer_data` 和属性复制，含设备同步；CPU 不执行 |
| RGBA 转色 | swscale 上下文准备、色彩配置、QImage 分配及 YUV → RGBA 转换 |
| 输出至渲染同步 | RGBA 输出完成 → 此帧 `updatePaintNode` 开始；含邮箱、GUI 和场景图调度 |
| 纹理准备（CPU） | `createTextureFromImage` / `setTexture` 的 CPU 耗时；Qt 可能延迟实际 GPU 上传 |
| 准备至 Qt 呈交 | 纹理准备完成 → 包含该新帧的 `frameSwapped`；不是扫描完成 |
| 组帧至 Qt 呈交 | 同一帧本机完整 AU 重组 → `frameSwapped`；不含采集、编码及网络传输 |

单调微秒时基经 packet 引用计数元数据关联到实际输出帧，PTS 同时保留组帧起点。
首包时间不随重复分片更新，乱序和多帧交错也分别保留各帧起点，避免延迟/重排输出错误归属最新输入。
不按该时间戳新增播放缓冲。每阶段最多 512 样本，使用最近秩分位数；空数据为 `—`，
样本少时 P99 接近最大值，仅作长尾线索。解码调用可能不出帧或输出多帧，呈现还会合并最新帧，
各阶段样本集合不同，不能将各项均值或 P99 相加声称为完整延迟。
来源切换/重配清空对应统计；每 250ms 发布值快照，不按每帧刷新 QML 文本。

本轮设备及原生渲染测量见[分阶段测量记录](design/video_stage_measurement.md)。

部署诊断可在启动前设置环境变量 `PIP_VIDEO_DECODER=cpu|auto|d3d11va|vaapi|cuda`；未设置时使用界面保存值。
显式后端还可配 `PIP_VIDEO_DEVICE`（D3D11VA 为枚举出的十进制 DXGI 编号，VAAPI 为 render 节点，
CUDA 为 FFmpeg 设备编号）。无效指定回退 CPU 并记录原因；auto 忽略显式 device。
这些是本地部署覆盖，不是网络协议配置，不写入图传 INI；设置和诊断均显示正在生效的环境覆盖。

当前硬件帧下载至 CPU，再由 swscale 转为 `RGBA8888`，沿用 Qt 纹理显示接口；这不是零拷贝，
不会因启用硬解就保证更高 FPS。颜色矩阵、有限/全范围和 SAR 从原始硬件帧复制，
不把驱动像素格式当作色彩标记。后续 GPU 纹理共享需单独验证 Qt 后端、同步、设备一致性和生命周期。
NV12 下载帧先用 swscale 无损拆成 YUV420P，再复用平面 YUV 的等尺寸 RGBA 快速转换；
中间帧仅解码线程持有、按规格复用，最大约 3 MiB；其他格式保留原转换路径。
该路径对照平面 YUV 参考验证矩阵、范围、通道及图像所有权，不改变编码分辨率或新增播放缓存。
CPU 回退仍禁用此前出现死锁的 slice/WPP 内部并行。

诊断实现已通过 Windows/Qt 6.9/MinGW 构建、格式和 QML 静态检查，完整 CTest 为 8/8。
人工时钟测试覆盖稳定速率、间隔抖动、low 样本不足、停流、序号回绕、窗口过期与缓存上限；
真实 UDP 回环覆盖统计发布、解码输出、Qt 呈交、断流清空和三种窗口三档 UI 边界。
截图使用项目自产短样本及测试节拍，不是 1080p60 吞吐基准；自动硬解的后续短测见文末，
Ubuntu、硬件矩阵及真实码流长稳性能尚未验收。

Esc 打开/关闭客户端菜单，全屏下仍优先开菜单；F11 切换全屏。
菜单默认进入当前会话，左侧包含图传设置、显示设置和运行诊断；图传只是一个分区。
侧栏始终提供继续画面和返回欢迎页。菜单打开期间继续接收。
图传分区可保存并开始接收或停止接收；关闭菜单不停止图传，也不提交编辑草稿。
同次打开期间切换分类保留草稿，重新打开菜单恢复已保存配置。
返回欢迎页释放监听端口并清空画面；再次进入恢复配置并开始监听。
当前业务叠层为空，详细错误在设置内显示；后续业务字段不属于视频纹理内容。
客户端菜单采用中性灰侧栏和橙色选中/动作色，图传分区保留会话摘要、监听表单及只读协议规格。
会话分区按网络、身份和连接状态分组；会话和图传表单滚动，底部保存/断开动作固定。
菜单居中，中档最大 1120×740 逻辑像素，窗口不足时保留水平 24、垂直 40 像素边距。
文字、图标、按钮高度和菜单最大尺寸只由 UI 档位决定；窗口仅改变可用空间、位置和列宽。
小窗口内容滚动，调整窗口不重置分区或草稿；下拉使用单向箭头和 Qt 键盘导航。
显示分区修改已有 UI 三档和全屏偏好；诊断只展示当前可取得的运行信息。
图传设置开放本机监听地址、UDP 端口、首个分片编号及本地解码设备。端口可修改，标签明确标注默认 3334，
修改后需与发送端目标端口一致；不会自动通知或修改发送端配置。
协议规格以只读信息显示：UDP / H.265 HEVC、官方 1920×1080 / 60 帧每秒、8 字节大端包头、
每包最多 1400 字节（负载最多 1392 字节）及无重传。这些是协议约定，不是当前流的测量结果。
超时、缓存和解码策略保留为内部策略，不开放编辑。
实际发送端 IP 和 UDP 源端口来自当前锁定来源，只读且不保存；未发现、停止或停包一秒后清空。
来源识别发生在包可进入组帧时，不要求已成功解码，也不表示来源已认证。实际来源不代替本机监听配置。
所有控件使用独立 UI 档位，提供悬停与键盘焦点反馈；小窗口只滚动表单，底部操作始终可见。
RMUC 继续保留原占位页；视频监听不依赖 MQTT。当前会话分区可独立启动 MQTT，见[本地接入](local_integration.md)。
视频生命周期由 C++ MatchSession 统一管理；会话运行时 UDP 绑定与 MQTT 使用同一个本地 IPv4，
视频地址在图传分区只读，UDP 端口仍可改（默认 3334）。停止视频不停止 MQTT，
断开 MQTT 不停止当前视频；离开比赛页停止全部链路，暂停视频不会因 MQTT 重连而重启。

配置保存在 Qt `AppConfigLocation/video.ini`，整组验证、原子保存，写失败保留原会话。
文件损坏时整体回退默认显示值且禁止监听，用户重新保存后恢复。

| 配置 | 默认 | 范围与含义 |
| --- | --- | --- |
| address | 0.0.0.0 | 本机数字 IP；默认所有 IPv4 接口。不是发送端 IP，不解析域名、不加入组播 |
| port | 3334 | 整数 1–65535，官方监听端口 3334 |
| index_base | 0 | 0 或 1，必须匹配发送端；0 是工程初始选择，官方未规定 |
| decoder | auto | `auto`、`cpu` 或探测列表的设备身份 key；仅本地选择，不发送给裁判系统 |

需要允许系统防火墙接收对应 UDP 入站数据；程序不会自动修改防火墙。

## 网络连接与分片编号

官方 §2 指定 MQTT 服务器为 `192.168.12.1:3333`，自定义终端本机 IP 为 `192.168.12.2`。
视频采用独立的 UDP 接收：发送端向终端的 3334 端口发送数据，本程序监听、重组、解码后显示，
没有 RTSP URL、拉流请求或 MQTT 视频订阅。官方该节未单列 UDP 源 IP/源端口，
不能把 MQTT 服务器地址写成已确认的视频源地址。

官方设备接入时，先在系统中把连接裁判系统席位 RJ45 的以太网网卡配置为官方终端地址 `192.168.12.2`，
子网掩码等参数按设备网络说明配置；本程序不会设置系统网卡 IP。
仅视频预览可保留 `0.0.0.0`（所有本机 IPv4 接口）；正式会话会收紧到所选网卡已有的
`192.168.12.2`，端口填 `3334`，保存并接收。`0.0.0.0` 不是发送目标地址，
`127.0.0.1` 仅用于同机测试。设备连接及发送行为仍需官方硬件联调确认。

“首个分片编号”（配置项 `index_base`）表示每一帧内的 UDP 小包从 0 还是 1 编号。
例如同一帧拆成三包，编号可能是 `0,1,2`，也可能是 `1,2,3`；不是帧号、端口或画质选项。
重组器按编号拼回完整帧，再交给 HEVC 解码器。官方没有写明起点，目前 0 是工程初始选择，
必须根据发送端实现或抓包确认，不能声称是官方默认值。普通裸 H.265 / RTP / MPEG-TS UDP 流
不符合本项目的 8 字节包头格式，不能直接接入当前接收器。

## 协议和工程策略

依据 [2027 协议 §2](protocol_2027.md)：8 字节大端头（uint16 帧号、uint16 分片号、
uint32 帧字节数），每包最大 1400 字节，负载最大 1392 字节；标准 HEVC 1080p60，无重传。
按完整 Annex B 访问单元交给 FFmpeg，不能将带头的数据报直接当裸 HEVC 或 MPEG-TS 播放。

下列限制是保护实时链路的工程策略，不声称官方规定：

- 每帧最多 2 MiB / 4096 分片，最多 4 帧同时组装；组帧期限为从首片起单调时钟 150 ms。
- 接受可变长度分片、乱序和相同重复；长度冲突、同序号不同内容、缺片、超时帧丢弃。
  连续分片序号与累计字节数同时满足才输出，绝不将部分帧送解码器。
- 16 位帧号按半区间比较处理回绕；已输出更晚帧后不回放旧帧。
- 单会话锁定首个有效候选来源的 IP + UDP 源端口，避免混帧；该来源停包 1 秒后重新锁定。
- 来源或解码帧序列跳变后清除解码上下文和旧参考帧，保留设备，等待可解码关键帧。
- 一秒没有成功解码画面就清屏，不用旧画面冒充实时视频。收到码流但不能解码时错误留在设置。
- 系统 UDP 接收缓冲请求 8 MiB（实际由 OS 限制）；每轮最多处理 128 包，持续检查停止/超时。

这套策略需用官方发送设备核实分片起始序号、访问单元边界和关键帧恢复行为。

## 线程、缓存与渲染

`VideoReceiver` 由主程序持有，公开方法仅 GUI 线程调用；`sourceAddress/sourcePort` 是 GUI 只读快照。
接收线程独占 QUdpSocket、VideoAssembler；其子解码线程独占 HevcDecoder 和全部 FFmpeg/硬件资源。
两线程之间最多暂存 3 个完整 AU，每个最多 2 MiB；短锁入队，不等待消费进度。
队列满时清空旧待处理 AU、递增参考链代数，保留最新 AU，下一次解码重开 codec 等待关键帧。
来源超时或帧号缺口同样使旧代失效；已在途解码的旧代输出也不能重新覆盖清屏或新来源。
初始化慢于收帧也可能溢出，需要下一携带参数集的关键帧恢复；没有按时间平滑播放或绝对排队时限保证。
修改队列代数及发布图像统一先取邮箱锁再取队列锁；FFmpeg/驱动调用不持锁。
停止先中断收包，再请求解码停止、清空/唤醒队列并 join 解码线程，之后释放队列及接收线程。
当前驱动/解码调用仍须完成才可 join；socket、FFmpeg 对象各在所属线程释放，全程不访问 QML。
QML engine 先析构，再释放接收器，避免悬空绑定。

FFmpeg 软件 HEVC 解码最大 1920×1080，编解码器内部使用单线程；解码运行在独立解码线程。
实流故障现场显示 FFmpeg 7 的 slice/WPP 并行停在 avcodec_send_packet 内部等待，
GUI 的停止/重配置又同步等待接收线程，造成界面无响应，因此基础路径禁用内部并行。
不启用增加帧排队的 frame threading；1080p60 性能需在目标设备实测。
像素先转换为 CPU `RGBA8888`（8 bit）；YUV 矩阵使用流中 BT.601/709/2020 标记，未标注 HD
使用 BT.709，区分有限/全范围。此基础路径不提供 HDR 色调映射。
显示只用最新帧，不按 PTS 排队；重组/超时用 QElapsedTimer 单调毫秒，跨线程诊断用 steady_clock 单调微秒。
没有墙钟同步，不把到达时间声称为相机采集时间或端到端延迟。

跨线程单槽邮箱由互斥锁保护，只发布不可变 QImage，共享后不修改；来源端点也在同锁下按转换发布。
工作线程更新邮箱时安排合并队列调用，GUI 被主动唤醒取最新帧，不再等待 16ms 定时轮询。
同一会话至多一个待处理唤醒，不在事件里携带图像；GUI 取走时在同锁内清除排队标记，
保证随后到达的帧可再唤醒。停止会递增 GUI 独有代数，旧唤醒不能覆盖新会话或复活画面。
来源只在获得、改变或清空时通知 QML，无逐帧/逐包队列堆积。
VideoView 在 Qt 场景图同步阶段上传纹理，纹理由节点持有，
只在新帧/重建节点时上传，窗口缩放只更新矩形。软件场景图也可运行。
用户态组帧最多 8 MiB，待解码 AU 最多 6 MiB，另有一个在途解码 AU 最多 2 MiB；
加单槽/GUI/纹理每张最大约 7.9 MiB；此外还包括 FFmpeg 参考帧、
解码线程、驱动与系统 socket 缓存，不能把这些数值当进程总内存上限。

## 2026-11-12 收包与解码隔离及尾延迟诊断

针对平均约 60fps、OUT low 显著偏低的反馈，将 UDP 收包/重组与解码分为两线程，
通过有界 AU 队列交接；禁止以无界视频缓存掩盖卡顿。设备初始化及解码/下载停顿不再同步阻塞读包。
队列溢出、来源超时或帧号缺口均递增参考链代数，拒绝在途旧代输出，保留设备后等待关键帧恢复。
