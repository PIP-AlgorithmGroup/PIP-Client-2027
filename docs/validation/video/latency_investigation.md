# 图传本机延迟排查

日期：2026-11-13。用户截图中的完整组帧至 Qt 呈交均值 14.65ms、P95 22.96ms。
该截图的排队均值 0.03ms，codec 调用 0.26ms、硬件下载 2.81ms、RGBA 转色 4.17ms，
RGBA 输出至渲染同步 5.22ms、准备至呈交 2.16ms；不能把各阶段 P95 相加当总延迟。

## 结论与边界

确认一个可修复的主开销：当前 FFmpeg 7 的 NV12 直接转 RGBA 路径比同尺寸平面 YUV 转换慢。
通过无损拆平面后转色降低 CPU 成本，保留硬解、色彩矩阵与范围，不积累视频缓冲。
硬件下载包含 GPU 解码完成等待与 CPU 下载，不能仅按 codec 调用的 0.26ms 宣称完整硬解耗时。
剩余主耗时是下载/同步与 Qt GUI/渲染/呈交等待；Qt 基础渲染循环对照更差，未替换现有循环。

新增首包读出至呈交和整个解码调用的直接统计。仍未测到物理屏幕亮起的时刻，
因为 Qt `frameSwapped` 不提供显示器像素实际扫描时间。应用读包前的内核排队也未测量。
真正“网卡收到 → 屏幕看到”须结合内核时间戳及高帧率摄像/光电或可靠显示时间戳验收。
以下本机数字不冒充物理端到端延迟。

## 复现环境与假设检验

Windows 11、Qt 6.9、FFmpeg 7、MinGW 13.1，Intel i7-14700HX / RTX 4070 Laptop GPU。
Qt 报告测试屏幕 165Hz，刷新周期约 6.06ms；这不是对每帧实际呈现时刻的测量。
测量时用户原客户端、MockServer、NVENC 编码器仍在运行，存在并行媒体负载；没有停用其他应用或改驱动、系统计时器。

1. 转色路径假设：相同 NV12 图像改用平面 YUV 快速路径后成本应显著下降。直接比较验证成立。
2. 硬件下载假设：GPU API 提交很短，但下载等待仍可能占毫秒级。阶段成本验证成立，不能再细分为纯 GPU 执行或纯复制。
3. GUI/渲染循环假设：若现有线程渲染循环是主要浪费，切换 Qt `basic` 应降低等待。运动 GOP 对照更慢，未采用。
4. 输入/后台负载假设：若源本身存在长间隔，RX/OUT low 不能单独归因于解码。独立发送源测得 1% low 约 25–32fps，验证存在输入节拍抖动。

原生基线命令为 `welcome_ui_test hdVideoReportsActualBackendAndPresentation`，
`QT_QPA_PLATFORM=windows`、`QSG_RHI_BACKEND=d3d11`，逐次设置 `PIP_VIDEO_DECODER=auto/cpu`。
该性能反馈回路先记录基线，再单变量验证；没有将依赖机器负载的毫秒阈值设为通用测试断言。

## 独立转色对照

同一张 1920×1080 NV12 图像，预热 20 次、测量 120 次，串行运行，无缩放：

| 路径 | 均值 ms | P95 ms |
| --- | --- | --- |
| 原 NV12 → RGBA，bilinear | 3.83 | 4.49 |
| NV12 → YUV420P → RGBA | 0.92 | 1.15 |
| NV12 → RGBA，fast bilinear | 3.85 | 4.79 |
| NV12 → RGBA，point | 3.55 | 4.08 |

收益来自布局及转换路径，不是简单降低缩放算法质量。
FFmpeg 7.1 源码 `libswscale/swscale_unscaled.c` 的 `ff_get_unscaled_swscale` 分别提供
NV12→YUV420P 和平面 YUV→RGB 的等尺寸转换入口，NV12 不进入后者的平面 YUV 专用分支。
动态 swscale 的不同输入路径已用实际二进制对照，不仅凭源码推测。

## 原生 UDP → 解码 → Qt 呈交

以下均为取快照时最近 1 秒统计，包含约 60 个解码/呈交样本；短测之间后台负载有变化，
不能把不同运行的均值差全部归功于一个改动。源调度、刷新相位也影响长尾。

| 同样重复 IDR / 60Hz | 原路径 GPU（两次） | 快速转色 GPU | 快速转色 CPU |
| --- | --- | --- | --- |
| 转色均值 ms | 9.30 / 11.39 | 2.50 | 1.87 |
| 组帧至呈交均值 ms | 22.57 / 29.02 | 12.16 | 11.92 |
| 组帧至呈交 P95 ms | 28.73 / 47.94 | 16.41 | 17.22 |
| OUT fps | 57 / 56 | 60 | 57 |

再生成 240 帧 testsrc2 运动样本：HEVC NVENC，1920×1080 / 60fps，4Mbps，
GOP=60、B 帧=0、前瞻=0、preset=p1、tune=ull，携带 AUD。
这些参数与当前 MockServer 的编码模式对应，但样本未包含服务器的动态文字和真实采集，不是原始实流回放。
每组正常事件循环运行 10 秒，末尾取最近 1 秒快照，按官方 UDP 分片发送。

| 运动 GOP 快速转色 | GPU 默认循环 | GPU 默认重复 | CPU 默认循环 | GPU basic 循环 |
| --- | --- | --- | --- | --- |
| 完整解码均值 ms | 5.78 | 5.14 | 5.26 | 7.55 |
| 首包读出→呈交均值 ms | 12.97 | 12.64 | 12.72 | 18.26 |
| 首包读出→呈交 P95 ms | 17.65 | 16.26 | 18.16 | 26.11 |
| OUT fps | 59 | 60 | 58 | 57 |
| 本地待解码累计丢弃 | 0 | 0 | 0 | 0 |

默认 GPU 重复运行快照：重组均值 0.126ms、解码排队 0.021ms、codec 调用 0.306ms、
下载 2.495ms、转色 2.144ms、输出至渲染同步 5.020ms、准备至 Qt 呈交 2.287ms。
该输入下重组/队列并非主要耗时，不应通过减小队列或抛弃更多帧解释当前约 7ms 呈现等待。
165Hz 刷新相位与 Qt/系统调度是呈现等待的候选来源，现有测量不能再细分出每个原因的精确占比。
没有通过禁用同步、全局调高计时精度或系统设置换取表面数字改善。

核对后可排除“程序固定等 10/16/250ms 再处理视频”的解释：socket 和队列的 10ms 是空闲等待上限，
有数据即唤醒；GUI 用合并事件取最新帧，不是 16ms 轮询；250ms 定时器只刷新统计文本。
swscale 的颜色配置相同则直接返回，本轮未把它误判成逐帧重建色彩表。

## 测量接口与回归

Esc 运行诊断顶部显示“首包读出至 Qt 呈交”“解码总耗时”，随后是各阶段。
首包时间随组帧、队列和 FFmpeg 引用计数元数据传递；重复分片不刷新起点，乱序帧各自关联，
延迟/重排输出不借用最新 AU 的时间。来源代数变化仍拒绝旧帧。
解码总耗时包括 packet 准备、回退、下载和转色，直接计时，P95 不由子项相加。
组帧耗时样本为进入解码且代数有效的 AU，首包至呈交样本为真正呈交的帧。

测量命令增加可选 `PIP_VIDEO_TEST_STREAM`（含 AUD 的 HEVC Annex B，最多 64MiB）、
`PIP_VIDEO_TEST_DURATION_MS`（2500–30000）。默认测试仍使用已有单 IDR，避免依赖外部编码器。
`VIDEO_MEASUREMENT` JSON 同时报告源 AU 数、屏幕报告刷新率、渲染循环及阶段快照。
本机测量日志和生成 GOP 仅保留在忽略的 `.cache/archive/flat/latency_*`，不提交机器专用产物。

颜色回归覆盖 BT.601/709/2020、全/有限范围、三种尺寸、规格变化、NV12/平面布局切换、
黑电平、RGBA 通道和输出图像独立所有权；与独立的平面 YUV swscale 参考逐像素一致。
另覆盖首包乱序/重复/多帧交错/未知时间、队列元数据及 CPU/实际 GPU 帧关联。
Ubuntu 构建、Intel/AMD/VAAPI 实机、真实物理屏幕延迟和 30 分钟长稳仍未验收。
当前原客户端窗口的 Computer Use 读取授权超时，未获得其当前实流截图 A/B；
用户提供的原始截图与独立原生测试分别记录，不能将后者当作前者的完整复现。

最终 Windows 完整 CTest 11/11 通过，包括新增转色测试、真实硬件解码、UDP/恢复及离屏界面回归。
clang-format、qmlformat 一致性及差异空白检查通过；原生性能测量与完整回归分开执行。
主程序完整构建、qmllint 通过；已重启本地客户端加载新产物，实际实流仍需重新进入 RMUL 后复核。
