# 呈现等待与解码恢复诊断验证

日期：2026-11-15。本轮增加诊断观测，不据此宣称截图中的卡顿已经修复。

## 观测范围

- 保留原 `guiWait`，按同一组实际进入场景图的新帧拆为 `mailboxWait`、`guiPrepare`、
  `renderWait`；分别观测解码输出到 GUI 取帧、GUI 处理、请求刷新到场景图同步。
- 20ms GUI 精确定时器统计超出目标周期的延迟，与有无新视频帧无关，每秒写入日志。
- 队列清空和解码器实际重置分开记录，以会话代数、参考链代数和协议帧编号关联。
  缓冲最多 32 个事件，每条日志最多 4 个，覆盖计数显式报告；停止接收时冲刷尾部。
- 输出帧编号与起点时钟一起通过 FFmpeg packet 引用计数元数据关联，不假定当前输入
  就是当前输出，硬件下载后保留属性；未知编号为 -1。

字段契约及解释见[图传接收诊断](../../modules/video_receiver.md#解码恢复事件)。

1920×1080 HEVC 回环输入，线程渲染循环，关闭垂直同步。三个新分段均有有效样本，
同组样本的均值之和与 `guiWait` 相等，允许 0.01ms 浮点误差。此项只验证观测路径，
不将测试负载下的快照当成卡顿根因或性能改善证据。

Ubuntu 验证在 WSL Ubuntu 22.04 进行，使用同版 Qt 6.12 与软件 FFmpeg。
硬件帧输出子用例因该 FFmpeg 未提供可用硬件后端而跳过，不计为 Ubuntu 硬解通过。

新增回归覆盖：

- 注入单调微秒的心跳：正常 20ms 周期不误报，120ms 实际间隔计为 100ms 超时，重置后重新预热。
- 真实 GUI 事件循环主动阻塞 120ms，确认 `runtime_snapshot.gui.heartbeat` 能观测到停顿。
- 真实 UDP / CPU 解码从编号 1 跳到 3，确认清空队列、解码器重置事件及帧编号一致，且写入日志。
- 连续 20 次参考链重置产生 40 个事件，确认只保留最近 32 个并报告覆盖 8 个。
- 消费者取走溢出后最新帧，不改变已保存的溢出前深度和丢弃数量；后继显式重置有独立原因。
- 接收超时清屏后来源解锁，记录 `source_timeout`；停止接收后记录 `session_stop`。

## 溢出前证据补充

同日继续补充清队列前的固定证据：在途操作类别和运行年龄、最近一次 decode 的
codec/下载/转色/总耗时、最老待处理 AU 等待年龄、最近 8 次入队编号/间隔/接收批号，
以及最近用户态接收批次的 AU 数和首末入队间隔。不调整队列容量、参考链恢复或播放策略。
每条日志由最多 8 个事件缩为 4 个，为证据字段保留 16KiB 预算余量。

回归场景包括人工时钟下 50ms 在途解码与 48ms 最老 AU 等待、同批四个 AU 的 0.001ms
相邻入队、历史上限 8 项、空闲/重置及无样本语义、旧代调用返回后固定证据不变、
真实线程阻塞时生产者仍能入队、真实 CPU 解码的输入编号/代数和分段耗时关联、
批量日志完整性（不触发 `fieldsOmitted` 或深度截断）。这些确定性输入用于验证测量契约，
不是用户会话的实测性能。

补充实现验证：Windows 完整构建及 18/18 组 CTest 通过，最终版本的队列与批量日志
专项重新通过；Windows 原生 threaded / Direct3D 11 / NVIDIA D3D11VA 的 1080p
播放专项通过。Ubuntu 22.04 完整构建及 17/17 组 CTest 通过（offscreen/software，
硬件输出子用例仍因软件 FFmpeg 跳过）；clang-format 19 和差异空白检查通过。
此次未修改 QML，未重新运行 QML 静态检查。尚未用新增证据复现用户会话中的过载，
不能据此认定驱动停顿或批量交付中的任何一种为根因。
