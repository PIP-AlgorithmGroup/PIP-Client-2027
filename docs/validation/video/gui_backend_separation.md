# GUI 与后端边界检查（0.2.0-alpha.1）

本记录检查 GPU 视频分支相对 main 的六个提交，并复核本轮发布前修正。
结论是后端执行与 QML 交互已经分层，持续通信和视频数据通路独立于 GUI；
不是把全部业务对象或全部业务执行迁离 GUI 线程。

## 实际职责

| 模块 | 执行位置与边界 |
| --- | --- |
| QML | 表单草稿、格式展示、菜单、导航和动作转发；不解析 MQTT/Protobuf、串口或视频协议 |
| AppController / MatchSession | GUI 线程协调对象，管理导航、状态、生命周期与结果应用 |
| DataPipeline / MqttWorker | GUI 接口加 MQTT 工作线程；网络、协议收发和控制发送在后台 |
| SerialController / SerialWorker | GUI 接口加串口线程；接收、解析及到 MQTT 的控制转发不经 GUI 逐帧交付 |
| VideoReceiver | GUI 接口；UDP 接收/组帧与解码各在后台，最新不可变帧放单槽邮箱 |
| PresentationWindow | GUI polish/主动同步 HUD，专用呈交线程独占 GPU/场景图资源，直接消费邮箱 |
| 系统查询与会话保存连接 | 网卡健康检测、手动网卡/串口枚举、会话网络校验和原子保存后台执行，GUI 应用值快照 |

图传正常 D3D11/OpenGL 独立模式下，呈交线程不反向阻塞等待 GUI；GUI 忙时复用已同步 HUD。
主线程主动同步可等待呈交线程，不能由此推导所有交互无等待。软件/未覆盖 API 保留原循环。

## 仍在 GUI 的执行

- `VideoReceiver::configure()` 的图传配置和 `SerialController::configure()` 的串口配置仍同步校验和写盘。
- `AppController` 的本地偏好读取/保存仍同步；这是交互设置路径，不是持续视频或控制转发路径。
- 链路 stop、资源回收和析构可能同步等待工作线程；不可取消的 OS 枚举仍可能拖延退出。
- 展示状态整理、信号通知和界面输入仍由 GUI 事件循环驱动；GUI 忙时 HUD 数值及输入会延后。

若后续目标改为“GUI 不做任何文件 I/O、所有启停均可取消”，需要继续异步化以上路径并验证
取消/退出协议，不能将当前独立视频管线等同于该目标。当前性能收益不依赖完成这些后续工作。

## 本轮审查

规范轴发现一个跨线程错误状态读取：阻塞调用返回后，呈交线程仍可更新 `QString`。
改为在呈交线程调用内复制错误快照，GUI 返回后只消费快照。需求轴发现独立模式计时标签
仍写 GUI/同步等待，现按 `presentationLoop` 切换为呈交线程取帧，并标明兼容项。
其余邮箱、旧代输出丢弃、唤醒合并、资源回收和平台回退未发现明确合入阻断问题。

完整功能回归、GUI 阻塞期间继续呈交与延迟证据见[独立呈交验证](independent_presentation.md)。
Intel/AMD、混合显卡、原生 Ubuntu VAAPI 和长期驱动恢复仍须独立实机验收。
