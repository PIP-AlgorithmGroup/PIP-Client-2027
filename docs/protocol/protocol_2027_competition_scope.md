# 2027 MQTT Topic 赛事适用范围：UL / UC

本文只分类 MQTT topic；串口字段仅作为对应业务的关联说明。UL 默认指联盟赛 3V3，步兵对抗的额外差异单列。UC 指超级对抗赛。

基线：通信协议 V1.0.0（20261029），比赛规则及参赛手册 V1.0.0（20261015）。核对日期：2026-11-16。

下表使用来源简称：**P** 为通信协议，**U** 为 UL 比赛规则，**C** 为 UC 比赛规则；版本及文档全名见第 8 节。`p.` 均指正文印刷页码，这三份 PDF 的阅读器页序为印刷页码加 1。

**“裁剪”仅指按赛事隐藏无对应业务的显示项、关闭无依据的操作，不删除 proto 字段、不改变数组布局，也不表示服务器不会发送。**两份参赛手册没有提供逐 MQTT 字段的可用性清单。

判定性质分为：**明文**（原文直接给出限制）、**推导**（协议字段含义结合赛项机制得出的业务判断）、**待确认**（不足以定为不可用）。除个别串口位明确写“仅 RMUL 适用”外，下文 MQTT 赛事分类多数属于推导。

## 1. 分类结论

| 分类 | Topic 数量 | 结论 |
| --- | --- | --- |
| 仅 UL 使用 | **0** | 当前 MQTT 定义中没有可确认的 UL 专属 topic |
| 按规则推导 UL 无对应业务、UC 使用 | **11** | 科技核心、能量机关、飞镖、雷达、哨兵特殊控制等，见第 3 节；不是官方 MQTT 禁用清单 |
| 两赛共用，部分字段需裁剪 | **17** | 比赛、机器人状态、经济、复活、输入等，见第 4 节 |
| UC 用途明确，UL 提供范围待确认 | **4** | 定位、地图点击和路径，见第 5 节 |
| 合计 | **32** | 覆盖项目两份 proto 中的全部 MQTT topic |

“UL 不用”指规则没有对应业务，不代表服务器一定不发该 topic。下文“关联串口”可能是同类指令、部分状态或执行后的结果，**不是官方声明的逐字段转换关系**。

## 2. 仅 UL 使用的 MQTT topic

**没有。**原文明确标注“仅 RMUL 适用”的控制区信息在串口协议中，当前没有明确的 MQTT 对应入口：

| UL 信息 | 关联串口字段 | MQTT 对应情况 |
| --- | --- | --- |
| R 高地控制区：激活 / 控制状态 | `0x0101 / event_data_2` bit 16–17 / 18–19 | 未定义明确对应字段 |
| B 高地控制区：激活 / 控制状态 | `0x0101 / event_data_2` bit 20–21 / 22–23 | 未定义明确对应字段 |
| 中央控制区：激活 / 控制状态 | `0x0101 / event_data_2` bit 24–25 / 26–27 | 未定义明确对应字段 |
| 本机器人检测到上述三个控制区的卡 | `0x0209 / rfid_status` bit 11 / 12 / 13 | 未定义明确对应字段；RFID 检测也不等于全场控制状态 |
| 赛事类型：UL 3V3 / UL 步兵对抗 | `0x0001 / game_type=4/5` | `GameStatus` 没有 `game_type` 字段 |

`event_data_2` 从串口数据段字节偏移 4 开始，上表 bit 编号相对该字段。依据：通信协议表 1-6、1-9、1-19。

不要用 `GlobalUnitStatus.outpost_R_status/outpost_B_status`、`GlobalSpecialMechanism` 或 `Event=5–8` 代替 UL 控制区：它们描述 UC 的基地 / 前哨阵地。

## 3. 按规则推导 UL 不用、UC 使用的 11 个 topic

这些结论共同依据 P 前言 p.1：“对于仅适用于某一赛项的兵种、机制或场地道具等条目，默认不适用于另一赛项。”每行再列出具体机制出处。不能把“不允许多机通信”单独解释为“不允许所有服务器指令”；两种链路不同。

| MQTT Topic | UC 中的业务 | 关联串口字段及对应程度 |
| --- | --- | --- |
| `GlobalSpecialMechanism` | 堡垒、R/B 前哨阵地、R/B 基地阵地计时；当前 `mechanism_id=1–6` 均为 UC 机制 | `0x0101 / event_data` 的堡垒激活、前哨阵地状态，以及 `event_data_2` 的基地阵地状态有关联；**没有同等的通用机制计时字段** |
| `AssemblyCommand` | 科技核心能量单元装配的开始、确认、取消与难度选择 | 未定义同等的常规串口装配命令。**不是模块化 42mm 发射机构安装** |
| `TechCoreMotionStateSync` | 科技核心位姿、能量单元步骤、四级协作和剩余时长 | 未定义可直接对应这组装配流程状态的常规串口消息 |
| `RuneActivateCommand` | 请求能量机关进入正在激活状态 | `0x0301` 子内容 `0x0120 / sentry_cmd` bit 24：哨兵确认启动能量机关；功能相关，但发送主体不同 |
| `RuneStatusSync` | 能量机关状态、已激活灯臂数、大能量机关平均环数 | `0x0101 / event_data` bit 1–2：小能量机关状态；bit 3–4：大能量机关状态。**不含灯臂数和平均环数** |
| `DartCommand` | 飞镖选靶、开关闸门、确认发射 | `0x0105 / dart_info` bit 6–8 反映当前选靶；`0x020A / dart_launch_opening_status`、`target_change_time`、`latest_launch_cmd_time` 反映闸门与最近操作。它们是下发状态，**不是同等上行指令** |
| `DartSelectTargetStatusSync` | 飞镖当前目标、闸门状态 | 当前选靶关联 `0x0105 / dart_info` bit 6–8；闸门关联 `0x020A / dart_launch_opening_status`。**枚举值不同，不能直接复制** |
| `RadarInfoToClient` | 雷达提供的双方机器人坐标和特殊标识 | 坐标关联 `0x0305 / map_robot_data_t`；标识关联 `0x020C / mark_progress` 的有效位。MQTT 还有“有标识但定位离线”状态，不能只由一个标识位完整还原 |
| `SentryStatusSync` | 哨兵姿态、姿态效果弱化、强化 | `0x020D / sentry_info_2` bit 12–13：姿态；bit 15：强化。`sentry_info_3` 提供姿态弱化前、强化姿态剩余时长；没有同名 `is_weakened` 布尔位 |
| `SentryCtrlCommand` | 指挥手请求哨兵补弹、回血、复活、切换姿态 | 同类自主决策功能见 `0x0301` 子内容 `0x0120 / sentry_cmd`：bit 0 复活，1 金币复活，2–12 补弹，13–16 远程补弹，17–20 远程回血，21–23 姿态。**位段 / 单调计数与 MQTT 指令编号不是同一编码** |
| `SentryCtrlResult` | 上述控制请求的指令编号和执行结果码 | `0x020D` 可反映部分兑换、复活、姿态状态；**没有等价的逐请求 `command_id/result_code` 回执** |

逐项依据如下，全部是业务适用性推导，不是逐 topic 的官方禁止条款：

| Topic | 协议定义位置 | 规则证据与推导范围 |
| --- | --- | --- |
| `GlobalSpecialMechanism` | P §2.2.6，p.56 | C §5.6.2，p.96–97 定义基地 / 前哨阵地，§5.6.4，p.102 起定义堡垒等增益点；U §3.2，p.21–28 与 §3.3.4，p.36–37 的场地 / 控制区清单没有这些道具。推导当前 ID 1–6 在 UL 无对应业务 |
| `AssemblyCommand` | P §2.2.21，p.68 | C §5.4.3，p.77 起定义科技核心装配；U §3.3.6，p.37–38 定义的是 42mm 安装，不能混同。推导 UL 不提供科技核心装配操作 |
| `TechCoreMotionStateSync` | P §2.2.22，p.69 | 同上，属于科技核心流程状态 |
| `RuneActivateCommand` | P §2.2.26，p.71 | C §5.6.3，p.97 起定义能量机关；U §3.2–3.3 的完整场地 / 机制范围没有能量机关。推导 UL 无该操作 |
| `RuneStatusSync` | P §2.2.27，p.71–72 | 同上，属于能量机关状态 |
| `DartCommand` | P §2.2.29，p.72–73 | U 表 3-1，p.16 只有 1/3/7；C 表 3-1，p.20 有飞镖，§5.7.3，p.110 起规定其控制。结合 P 前言推导 UL 无飞镖操作 |
| `DartSelectTargetStatusSync` | P §2.2.30，p.73 | 同上，属于飞镖状态 |
| `RadarInfoToClient` | P §2.2.19，p.67–68 | U 表 3-1，p.16 无雷达；C 表 3-1，p.20 有雷达，§5.7.4，p.112 起定义雷达机制。推导 UL 无雷达来源业务 |
| `SentryStatusSync` | P §2.2.28，p.72 | C §5.7.2，p.108–110 定义姿态、弱化和强化；U 表 3-5，p.20–21 给定哨兵性能，未定义姿态系统。属于机制缺席推导，不能声称 U 明文禁止该 topic |
| `SentryCtrlCommand` | P §2.2.31，p.73–74 | U §3.1.3 / 表 3-5，p.20–21：全自动、局内不可增加弹量；U §3.3.2–3.3.3，p.35：自动复活、金币仅换弹量。C §5.7.2，p.108–109 才定义指挥手干预及姿态。推导 UL 无这套 UC 控制业务，不单凭多机通信限制判断 |
| `SentryCtrlResult` | P §2.2.32，p.74 | 跟随上述 UC 控制请求的业务范围；并非独立的 UL 禁止回执条款 |

需要区分的三点：

- UL 哨兵全自动运行、不允许多机通信、局内不能增加允许发弹量，因此不能因其同为“哨兵”就启用 UC 哨兵控制。
- `SentryStatusSync.is_weakened` 是姿态效果弱化，不是 UL 自动复活后的“虚弱”。
- `RadarSingleRobotInfo` 是雷达辅助结构，不是第 33 个 topic；`RadarInfoToClient` 外层定义仍存在原文歧义，见[协议说明](protocol_2027.md)。

## 4. 两赛共用的 17 个 topic：UL 保留什么、裁剪什么

下表均有 UC 用途。UL 不能整条删除这些 topic，应按字段、枚举和机器人类型使用。

| MQTT Topic | UL 3V3 使用范围与 UC 差异 | 关联串口 |
| --- | --- | --- |
| `KeyboardMouseControl` | 人工操作兵种的键鼠输入；不得据此控制 UL 全自动哨兵 | 当前串口命令清单没有同等的键鼠消息，不能将 `0x0311` 当作其固定字段布局 |
| `CustomControl` | 自定义指令，按兵种控制权限使用 | `0x0311` 自定义数据，最多 60 字节 |
| `CustomByteBlock` | 机器人发来的自定义数据，按兵种通信权限使用 | `0x0310` 自定义数据，最多 300 字节 |
| `GameStatus` | 局号、比分、阶段、时间、暂停、胜者保留；`end_reason=1` 基地摧毁不用 | `0x0001` 对应阶段、剩余时间；`0x0002.winner` 对应胜者。串口没有完整的 MQTT 局号、比分、结束原因集合 |
| `GlobalUnitStatus` | 保留双方 1/3/7 血量、己方弹量、总伤害；基地 / 前哨字段及 4 号槽位不用。`total_CP_ally/enemy` 的 UL 数值映射待确认 | `0x0003` 有己方机器人血量、基地 / 前哨血量、伤害差、双方控制度；`0x0101` 有 UC 阵地状态。串口血量布局与 MQTT 8 项数组不同 |
| `GlobalLogisticsStatus` | 使用 `remaining_economy`、`total_economy_obtained`；不用 `tech_level`、`encryption_level` | `0x0208.remaining_gold_coin` 对应当前金币；没有等价的常规串口全局后勤消息 |
| `Event` | 使用 `event_id=1` 击杀、`16` 模块化 42mm 成功安装；不用 `2–15` | 没有统一对应的串口事件流；`0x0101`、`0x0105` 等只反映部分相关状态 |
| `RobotInjuryStat` | 使用伤害统计；不用 `dart_splash_damage` | `0x0206` 是即时本地伤害 / 命中信息，**不是本次存活的累计受伤统计** |
| `RobotRespawnStatus` | 使用待复活状态与总 / 当前读条；UL 无付费复活业务。`can_free_respawn` 表示可否免费复活，应保留；不能据此自动增加“确认复活”按钮 | `0x020D.sentry_info` bit 19–30 有 UC 哨兵免费 / 金币复活可用性及金币数；**没有通用复活读条的等价字段** |
| `RobotStaticStatus` | 使用身份、连接、存活、实际性能等；不套用 UC 经验升级机制。UL 3V3 的 3 号步兵有性能体系选择 | `0x0201` 有 ID、等级、血量、热量上限 / 冷却、功率上限等部分属性；不是完整一一对应 |
| `RobotDynamicStatus` | 使用血量、热量、射速、缓冲能量、已发 / 剩余弹量；UL 无已定义的远程回血 / 补弹操作。经验、升级差值和脱战状态在 UL 的字段意义待确认，不能直接列为禁用字段 | `0x0201` 当前血量；`0x0202` 热量 / 缓冲；`0x0207` 射击；`0x0208` 弹量；`0x020D` 有 UC 哨兵脱战等状态 |
| `RobotModuleStatus` | 按实际装备显示模块状态。`modular_42mm` 的 UL 权限取值待确认，不能当“已安装” | 无完整逐模块在线状态对应；`0x0201.power_management_*_output` 仅表示电源输出，**不等于模块在线** |
| `Buff` | UL 明确有防御、冷却、回血机制；其他类型的产生条件 / 映射不能套用 UC | `0x0204` 有回血、冷却、防御、易伤、攻击增益子集；不包含完整 MQTT Buff 类型与剩余时间 |
| `PenaltyInfo` | 判罚与超限机制保留 | `0x0104` 有判罚等级、违规机器人、次数；与 MQTT `penalty_type` 编码和覆盖内容不同 |
| `RobotPerformanceSelectionCommand` | 3 号步兵使用 `shooter/chassis`；不提供哨兵半自动切换 | `0x0201` 可反映部分选定性能的结果，但没有等价的性能选择上行指令 |
| `RobotPerformanceSelectionSync` | 同上，保留步兵性能同步；不把 `sentry_control=1` 用于 UL | `0x0201` 为部分实际属性，不直接给出这组选择枚举 |
| `CommonCommand` | 使用 `cmd_type=1/2` 在补给区买 17/42mm 弹量；`3` 主动确认复活待确认；不用 `4/5/6` 付费复活 / 远程补弹 / 远程回血 | `0x0301` 子内容 `0x0120` 仅有哨兵同类自主决策功能，不能套到 UL 重装 / 步兵；`0x0208` 可反映弹量和金币结果 |

| `RobotDynamicStatus.is_out_of_combat/out_of_combat_countdown` | P §2.2.11，p.61–62 | C §5.3.1，p.73、§5.4.2，p.77 将脱战与远程 / 补给机制关联；U §3.3.2–3.3.3 未定义同等用途 | **待确认：**缺少 UL 用途说明不是明确禁用条款。保留接收，不能推断 UL 服务端不存在脱战状态 |
| 两条 `RobotPerformanceSelection*` 的 `sentry_control=1` | P §2.2.23–24，p.69–70：0 自动、1 半自动 | U §3.1.3，p.20：“哨兵机器人需全自动运行”；C §5.7.2，p.108 明确可选自动 / 半自动 | **明文限制 + 字段推导：**UL 不开放半自动选择；`shooter/chassis` 仍按 U §3.1.2，p.18–19 保留步兵选择 |
| `RobotModuleStatus.modular_42mm` | P §2.2.12，p.62–63 定义“安装权限” | U §3.3.6，p.37–38 有安装机制；C §5.7.1，p.108 有权限解锁路径 | **待确认，不裁掉：**UL 同样有安装机制，权限字段的服务端值未明确；不能当作“已安装” |
| `Buff.buff_type` 各子类型 | P §2.2.14，p.63–64 | U §3.3.2.1，p.35 有回血；§3.3.5，p.37 有防御、冷却和隧道增益 | **仅能确认机制存在：**不能据此得出 Buff 类型 1/4/6/7 一律禁用，也不能仅因 UL 有隧道就确认类型 7 的具体编码映射 |
| `CommonCommand.cmd_type=3`；`RobotRespawnStatus.can_free_respawn` | P §2.2.25，p.71 定义“确认复活”；§2.2.9，p.59 只把布尔量定义为“是否可以免费复活” | U §3.3.2.2，p.35：“战亡的机器人可自动复活” | **待确认：**UL 自动复活明确；主动确认命令是否被接受未明确。免费复活状态字段本身没有应删除的依据 |

输入、自定义数据、判罚、常规血量 / 热量等保留项按 P 对应消息定义和 U §3.1.4（p.21）、§3.3.1（p.29–34）使用；没有将它们列入无依据的字段裁剪。

四个易错点：

- **控制度共用需求、数值语义不同：**UL 从 600 递减，UC 累计增加；协议把 `total_CP_*` 写为“累计控制度”，UL 具体映射未明确，不能自行按 `600 - 值` 换算。
- **42mm 安装两赛都有：**`Event=16` 不能删；科技核心装配 `AssemblyCommand` 则是 UC 机制。
- **复活两赛都有：**UL 自动读条复活，不意味着允许 UC 的主动确认、金币复活操作。
- **数组按原协议解析：**UL 无 4 号不等于可以重排 `robot_health`；`robot_bullets` 的长度和顺序原文未明确，不能照抄血量数组。

## 5. UL 提供范围待确认的 4 个 topic

这四条在 UC 有明确用途，但现有材料不足以断言“整个 topic 仅 UC 可用”。

| MQTT Topic | UC 用途 | 关联串口与 UL 待确认点 |
| --- | --- | --- |
| `RobotPosition` | 位置、朝向；指挥手终端可接收哨兵坐标 | `0x0203` 为本机器人 x/y/朝向，`0x020B` 为发给哨兵的己方部分机器人坐标。UL 的定位部署、提供范围待确认；UL 无 UC 指挥手哨兵链路 |
| `RobotPathPlanInfo` | 哨兵 / 半自动机器人的规划路径显示 | `0x0307` 为路径起点、49 组增量及发送者。UL 提供范围待确认；原文串口与 MQTT 对增量基准的描述有冲突，不能直接还原坐标 |
| `MapClickCmd` | 终端发起地图 / 机器人标记 | `0x0303` 下发目标坐标、按键、目标 ID、来源 ID，但不是同一消息布局。UL 角色授权待确认，不据此允许干预全自动哨兵 |
| `MapClickInfo` | 终端接收地图标记同步 | 同上，`0x0303` 为相关的机器人侧地图指令；UL 同步范围待确认 |

依据：通信协议 §1.3、§2.2.13、§2.2.16–18；UC 规则 §5.7.2；UL 规则 §3.1。

## 6. UL 步兵对抗的额外裁剪

第 3 节的 11 条同样不用；第 4 节还需按以下规则裁剪：

| Topic / 功能 | 步兵对抗处理 |
| --- | --- |
| `GlobalUnitStatus` | 仅 3 号步兵相关状态；没有控制区、控制度胜负机制、重装和哨兵 |
| `GlobalLogisticsStatus`、`CommonCommand` 的购买功能 | 无经济兑换业务；初始 200 发，局内不可增加 |
| `RobotRespawnStatus`、复活命令 | 无复活业务 |
| 两条 `RobotPerformanceSelection*` | 固定性能，无 3V3 的性能体系选择业务 |
| `Event`、42mm 相关状态 | 仅保留对应步兵业务，`Event=16` 和 42mm 安装不用 |
| `RobotDynamicStatus.current_health`、`Buff` | 有“弹丸伤害量 50% 回血”；但是否单独发布为 Buff 未明确，血量以服务端状态为准 |
| `GameStatus` | 使用阶段、时间、结果；首次扣血 / 首次发弹等胜负判据没有完整 `end_reason` 映射，不能仅凭该枚举自行重算胜者 |

逐项依据：U 表 4-1、4-2（p.39–40）明确仅 3 号、固定性能、“初始允许发弹量为 200 发，局内不可增加”和“回血与复活机制不适用”；§4.3.1（p.44）又明确伤害回血；§4.4（p.44）列胜负判据。无经济购买 / 性能切换业务是由固定参数和赛项完整机制范围推导，不能把 §4.1.2（p.40–41）对自定义终端的一般功能举例当作这些操作已在步兵对抗开放。

表 4-2 的“回血与复活机制不适用”不能覆盖 §4.3.1 明确新增的伤害回血。

## 7. 不能从这些依据得出的结论

- 无法证明某个 topic 或字段在 UL 一定不发送、固定为 0 或省略。
- 无法仅凭“UL 规则未写”就认定通用状态字段无效，尤其是经验、脱战、Buff 子类型。
- 串口与 MQTT 同属一个机制只说明业务关联，不能替代字段编码、权限和枚举的逐项核对。
- 本文不授权删除 proto 字段、重排数组、丢弃未知字段或更改官方消息定义。
